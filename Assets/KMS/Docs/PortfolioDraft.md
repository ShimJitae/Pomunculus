# 포트폴리오 초안 검토와 정리

> 직접 적은 포트폴리오 항목 6개를 실제 코드·프리팹·커밋 이력과 대조해서, 고칠 표현과 보완할 내용, 추가하면 좋은 소재를 정리한 문서입니다.
> - **1장**: 검토 요약 (먼저 고칠 것 5가지)
> - **2장**: 항목별 검토 (초안 → 확인한 사실 → 보완할 점 → 다듬은 문장)
> - **3장**: "이후 구현 예정" 수정
> - **4장**: 추가하면 좋은 내용
> - **5장**: 권장 목차
> - **6장**: 넣기 전에 준비할 것 (자료, 직접 채울 내용, 코드 정리)
>
> 기준: 2026-11-13, `feat/kwon/player` 브랜치 (커밋 `cd68df4`)
> 관련 문서: 소재별 상세 분석은 `PortfolioAnalysis.md`, 구현 과정은 개발 기록 3편(`PlayerBehaviorDevLog.md`, `ThrowAimIndicatorDevLog.md`, `PotionSlotMVPRefactorDevLog.md`)과 `PotionPrefabVariant.md`에 있습니다. 이 문서는 **초안을 어떻게 고칠지**에 집중합니다.

---

## 1. 검토 요약

초안의 6개 항목은 모두 실제 구현과 맞는다. 다만 지금 문장은 **"무엇을 썼는지"(API 이름)** 위주라서, 읽는 사람이 **"왜 그렇게 했고 무엇이 좋아졌는지"**를 알 수 없다. 먼저 고칠 것은 다섯 가지다.

| # | 고칠 것 | 이유 |
|---|---|---|
| 1 | 항목마다 **문제 → 판단 → 해결 → 결과** 순서로 쓴다 | "NavMesh 활용", "LineRenderer 활용"은 누구나 쓰는 기능이다. 차이는 판단 근거와 결과에서 난다 |
| 2 | **조준선 항목을 메인 소재로 올린다** | 조준선과 실제 궤적이 어긋나던 문제를 원인 3가지로 나눠 수식으로 고친 기록이 있다. 초안에는 이 내용이 빠져 있다 |
| 3 | **던지기 동기화에 "누가 판정하는가"를 넣는다** | 궤적을 각자 계산하면 착탄도 화면마다 일어난다. 피해를 한 번만 적용하는 구조(대상의 결정권자만 적용)가 이미 구현돼 있는데 초안에 없다 |
| 4 | **"포션 효과는 이후 구현 예정"을 고친다** | 효과를 조합하는 구조는 이미 구현됐다. 남은 것은 포션별 데이터 연결이다 (3장) |
| 5 | **빠진 소재를 추가한다** | 플레이어 FSM과 컴포넌트 분리, 멀티플레이 버그 2건 해결, 입력 버퍼는 초안에 없지만 강한 소재다 (4장) |

## 2. 항목별 검토

### 2-1. 플레이어 이동

**초안**: 마우스 클릭 위치로 이동 (NavMesh 활용)

**확인한 사실**
| 내용 | 위치 |
|---|---|
| **우클릭** 지점으로 이동한다. 누르고 있으면 0.1초마다 목적지를 갱신한다 | `PlayerInputReader.ReadInput` |
| 마우스 위치 → 지면 레이캐스트 → `NavMesh.SamplePosition`(반경 2m)으로 갈 수 있는 위치로 보정 → `NavMeshAgent.SetDestination` | `TryGetNavPointUnderMouse`, `PlayerMotor.MoveTo` |
| 회전은 Agent에 맡기지 않고 직접 한다 (`updateRotation = false`) | `PlayerMotor.RotateTowards` |
| 도착 지점 근처에서 느려지던 문제를 `autoBraking`을 꺼서 해결했다 | 커밋 `fa3b256` |
| 회피·넉백은 `agent.Move`로 처리해 NavMesh 밖으로 나가지 않는다 | `PlayerMotor.Displace` |
| 다른 플레이어의 캐릭터는 Agent를 끄고 위치 동기화 값만 따라간다 | `PlayerFSM.SetOwner` |

**보완할 점**
- "마우스 클릭"을 **우클릭**으로 정확히 쓴다. 좌클릭은 던지기다.
- 이동만 따로 쓰면 소재가 약하다. **플레이어 FSM 항목(4장 A) 안에 넣어** "이동·던지기·회피·피격을 상태로 관리했다"로 묶는 편이 좋다.
- 이동에서 내세울 것은 NavMesh가 아니라 **조작감 처리**다. 던지기나 피격 중에 누른 우클릭이 사라지지 않고 행동이 끝난 뒤 실행된다(`ConsumeMoveCommand`).

**다듬은 문장**
> 우클릭 지점을 NavMesh 위 좌표로 보정해 NavMeshAgent로 이동시켰다. 입력은 버퍼에 기록만 하고 상태가 꺼내 쓰는 구조라서, 던지기·피격 중에 누른 이동 명령도 행동이 끝나면 이어서 실행된다.

### 2-2. 주변 아이템 자동 줍기

**초안**: `Physics.OverlapSphereNonAlloc`으로 주변 픽업 아이템 탐지 후 인벤토리 추가

**확인한 사실**
| 내용 | 위치 |
|---|---|
| 반경 1.5m를 0.1초 간격으로 검사한다. 16칸 고정 버퍼를 재사용한다 | `ItemPickupController.Scan` |
| 줍기 전용 레이어만 검사한다. 내 캐릭터에서만 검사한다 | `pickupLayer`, `owner.IsMine` |
| 한 아이템에 콜라이더가 여러 개여도 한 번만 처리한다 | `detectedThisScan` (HashSet) |
| **재료는 바로 인벤토리에 넣지 않는다.** 줍는 쪽은 아이템을 숨기고 방장에게 요청한다. 방장이 먼저 온 요청 하나만 확정하고, 그 플레이어에게만 지급한 뒤 필드에서 지운다 | `MaterialPickup.HandlePickupRequest`, `PlayerFSM.SendGrantItem` |
| 포션은 감지한 클라이언트가 바로 인벤토리에 넣는다 | `ItemPickupController.PickupPotion` |

**보완할 점**
- "탐지 후 인벤토리 추가"는 **포션에만 맞는 설명**이다. 재료는 방장 확정을 거친다. 이 부분이 더 좋은 소재이므로 반드시 넣는다.
- 이 구조는 버그를 고치면서 만들어졌다. "방장이 아닌 플레이어가 재료를 줍지 못함"(커밋 `84dc861`)의 원인은 방장만 월드 오브젝트를 지울 수 있다는 것이었다. 요청 방식으로 바꾸면서 **두 명이 동시에 주워도 한 명만 받는** 구조가 됐다.
- `NonAlloc`을 쓴 이유를 쓴다: 0.1초마다 반복하는 검사에서 배열을 매번 새로 만들지 않기 위해서다. 프로파일러의 GC Alloc 화면을 한 장 붙이면 근거가 된다.
- **한계도 적는다.** 필드의 포션(`PotionPickup`)은 아직 네트워크로 동기화하지 않는다. 멀티에서 필드 포션을 쓰게 되면 재료와 같은 요청 방식으로 바꿔야 한다.

**다듬은 문장**
> `OverlapSphereNonAlloc`과 고정 버퍼로 0.1초마다 주변 아이템을 감지했다. 멀티플레이에서는 줍는 쪽이 방장에게 요청하고, 방장이 먼저 온 요청 하나만 확정해 지급하게 해서 중복 획득을 막았다.

### 2-3. 던지기 조준선

**초안**: 포물선 궤적은 LineRenderer 활용, `Physics.SphereCast`로 포션이 닿은 부분 체크

**확인한 사실**
| 내용 | 위치 |
|---|---|
| Shift를 누르는 동안 궤적 선(30구간)과 착탄 범위 원을 내 화면에만 그린다 | `ThrowAimIndicator.LateUpdate` |
| 궤적은 **실제 던지기와 같은 함수**로 계산한다 | `ClampToThrowRange` → `GetThrowOrigin` → `CalculateLaunchVelocity` |
| 구간마다 **실제 포션과 같은 반지름의 구**로 장애물을 검사해 선을 끊는다 | `DrawTrajectory`, `ThrownProjectile.TryGetCollisionSphere` |
| 범위 원의 반지름은 던질 포션 프리팹의 착탄 반경을 그대로 쓴다 | `ImpactRadius` |

**보완할 점**
- 이 항목의 핵심은 **"조준선이 실제 궤적과 어긋나던 문제를 고친 과정"**이다. 초안에는 결과만 있고 이 과정이 없다. 포트폴리오에서 가장 강한 소재이므로 메인으로 올린다.

  | 원인 | 해결 |
  |---|---|
  | 조준선은 공식으로, 실제 포션은 물리 엔진으로 움직여 낙하 지점이 달랐다. 물리 엔진은 0.02초 단위로 속도를 먼저 바꾸고 위치를 옮겨서 공식보다 `½·g·dt·t`만큼 낮다 (체공 1.5초에 약 15cm) | 발사 속도에서 반 스텝만큼의 중력을 뺐다 |
  | 포션에 랜덤 회전을 주는데 콜라이더가 박스라서 회전에 따라 닿는 범위가 달랐다 | 구 콜라이더로 바꿨다 |
  | 조준선은 두께 0인 선으로 검사하고, 실제 포션은 반지름 0.15m인 구였다. 콜라이더 중심도 피벗보다 13cm 높았다 | `Linecast` → `SphereCast`로 바꾸고, 던지기용 프리팹에서만 중심을 피벗에 맞췄다 |

- "SphereCast로 닿은 부분 체크"는 **왜 구인지**가 빠져 있다. "실제 포션과 같은 크기로 검사하기 위해서"라고 쓴다.
- **남은 차이도 적는다.** 조준선의 장애물 레이어는 지금 Default와 Ground뿐이다(`Player.prefab`의 `obstacleLayers`). 실제 포션은 적에게 닿으면 터지므로, 적이 궤적 사이에 있으면 조준선과 다르다. Enemy 레이어를 추가하면 해결된다.

**다듬은 문장**
> 조준선을 실제 던지기와 같은 함수로 계산하고, 포션과 같은 반지름의 `SphereCast`로 착탄 지점을 예측했다. 조준선과 실제 궤적이 어긋나는 원인을 물리 적분 오차·콜라이더 모양·검사 두께로 나눠 각각 보정했다.

### 2-4. 플레이어 UI (MVP 구조, 패널별 프리팹)

**초안**: MVP 패턴 활용, View를 하나하나 프리팹으로 관리 → 다른 팀원이 수정할 때 충돌을 줄임 (팀원이 인벤토리 작업 때 포션 슬롯을 가져가서 작업함)

**확인한 사실**
| 내용 | 근거 |
|---|---|
| `PlayerHUD.prefab`은 `StatPanel` / `StatusPanel` / `PotionSlot` 프리팹 3개를 중첩해서 구성한다. 상태이상 아이콘(`StatusEffectIcon`)은 실행 중에 생성한다 | 프리팹 참조 확인 |
| 패널마다 View 인터페이스, View, Presenter가 있다. Presenter는 일반 C# 클래스이고 `Dispose`에서 구독을 해제한다 | `Scripts/UI/` |
| HUD는 내 캐릭터에만 생성한다 | `LocalPlayerHUD` |
| HUD를 패널로 나눈 날(11-05, `3c10c0f`)에 팀원이 `PotionSlot` 프리팹을 인벤토리 Canvas에 넣어 장착 슬롯을 만들었다 (`b50bba5`) | 커밋 이력 |

**보완할 점**
- **두 가지 결정을 나눠서 쓴다.** 지금 문장은 "MVP라서 충돌이 줄었다"로 읽힌다.

  | 결정 | 얻은 것 |
  |---|---|
  | MVP 구조 | 표시(View)와 데이터(Model)가 분리된다. View는 받은 값만 그리므로 다른 화면에서도 쓸 수 있다 |
  | 패널별 프리팹 | 파일이 나뉘어 있어서 두 사람이 다른 패널을 고쳐도 같은 프리팹 파일을 건드리지 않는다. 프리팹 파일은 병합이 어려워서 효과가 크다 |

- **팀원 재사용 사례에는 뒷이야기가 있다.** 이 부분을 넣으면 훨씬 좋은 소재가 된다.
  1. 팀원이 `PotionSlot` 프리팹을 인벤토리에 가져다 써서 장착 슬롯을 빠르게 만들었다. (프리팹 분리의 효과)
  2. 그런데 장착 데이터를 인벤토리 UI와 플레이어가 **각각 따로** 갖게 됐다. 둘을 맞추려고 매 프레임 비교·복사하는 컴포넌트가 생겼고, 장착 정보를 저장할 수도 없었다.
  3. Model을 `PotionLoadout` 하나로 합치고 복사 컴포넌트를 삭제했다 (`779bc0f`, `3cd3e9c`).
  4. 그 결과 장착 상태를 저장하고 다른 클라이언트에 동기화할 수 있게 됐다 (`cd68df4`).

  "View는 재사용됐지만 데이터 주인을 정하지 않아 중복이 생겼고, 이를 리팩토링으로 바로잡았다"까지 쓰면 **잘된 점과 배운 점**이 함께 드러난다.
- "충돌을 줄였다"는 근거가 있어야 한다. 실제로 UI 프리팹에서 병합 충돌이 났던 일이 있으면 그 사례를, 없으면 "같은 프리팹 파일을 동시에 고치는 일을 없앴다"로 쓴다.
- **상태이상 아이콘은 아직 이미지가 연결되지 않았다** (`StatusPanelPresenter.GetIcon`이 항상 null). 아이콘 추가·갱신·제거와 남은 시간 표시는 동작한다. 영상을 찍기 전에 연결한다.

**다듬은 문장**
> HUD를 체력·상태이상·포션 슬롯 패널로 나눠 각각 프리팹과 MVP 구조로 만들었다. 팀원이 포션 슬롯 프리팹을 인벤토리에 재사용하면서 장착 데이터가 두 곳에 생기자, Model을 하나로 합쳐 매 프레임 동기화 코드를 없애고 저장·네트워크 동기화가 가능하게 했다.

### 2-5. 픽업 포션과 던지기 포션 구분 (프리팹 베리언트)

**초안**: 프리팹 베리언트로 나눔. 한 프리팹에 두 기능을 넣으면 충돌 (바닥에 놓은 포션이 바로 깨지면서 공격 효과 발생 등)

**확인한 사실**
| 내용 | 근거 |
|---|---|
| `Base`(모델·구 콜라이더·Rigidbody) → `Thrown`(`ThrownProjectile`) / `Pickup`(`PotionPickup`) 구조다 | 빈 병, 화염 포션 프리팹 6개 |
| Base에는 동작 스크립트가 없다 | 프리팹 확인 |
| 던지기용만 콜라이더 중심을 피벗에 맞췄다. 줍기용은 바닥 피벗을 유지한다 | `EmptyPotion_Thrown`의 오버라이드 |

**보완할 점**
- "충돌되는 문제"를 **원인까지** 쓴다. 이 내용이 이 항목의 핵심이다.

  | 문제 | 원인 |
  |---|---|
  | 바닥의 병이 닿자마자 터진다 | Unity는 **꺼 둔 컴포넌트에도 `OnCollisionEnter`를 호출**한다. 던지기 스크립트를 꺼도 착탄 처리가 실행된다 |
  | 던지자마자 던진 사람이 다시 줍는다 | 손 위치가 줍기 반경(1.5m) 안이다 |
  | 떨어뜨린 병이 공중에 떠 있다 | 던지기 스크립트가 중력을 끄고 직접 적용한다 |

- **버린 대안을 쓴다.** 한 프리팹에 두 기능을 넣고 플래그·레이어 전환으로 막을 수도 있었다. 그러면 상태 전환 코드를 계속 관리해야 한다. 베리언트는 두 동작이 한 오브젝트에 함께 있는 경우 자체를 없앤다.
- **베리언트라서 가능했던 일**을 하나 더 쓴다. 조준선 정확도를 위해 던지기용만 콜라이더 중심을 옮겼는데, 줍기용에는 영향이 없었다 (2-3과 연결).
- 위 문제를 **실제로 겪었는지, 설계할 때 예상했는지** 구분해서 쓴다. 겪었다면 재현 영상이 좋은 자료다.
- 가이드 문서(`PotionPrefabVariant.md`) 4장은 아직 BoxCollider를 안내한다. 실제 프리팹은 구 콜라이더이므로 문서를 맞춘다.

**다듬은 문장**
> 포션 프리팹을 모양만 가진 Base와, 던지기용·줍기용 베리언트로 나눴다. 한 프리팹에 두 동작을 넣으면 꺼 둔 컴포넌트에도 충돌 이벤트가 호출돼 바닥의 병이 터지는 문제가 생기는데, 상태 전환 코드 대신 구조로 이 경우를 없앴다.

### 2-6. 포션 던지기 멀티 동기화

**초안**: 던진 포션을 네트워크 오브젝트로 만들지 않고 위치·초기 속도·중력·포션 Id만 보내 각 로컬에서 궤적 계산 → 지연에 따라 PC마다 포션 위치가 다를 수 있음 (지연 보상 추가 구현 가능성)

**확인한 사실**
| 내용 | 위치 |
|---|---|
| 던질 때 발사 위치·초기 속도·중력(Vector3 3개)과 포션 Id(int)를 **한 번만** 보낸다 | `PlayerFSM.SendThrow` |
| 던진 사람 화면은 즉시 실행하고, 나머지는 받는 대로 실행한다 | `WorldRPCTarget.All` |
| 받은 값으로 각 클라이언트가 투사체를 만들어 물리로 움직인다 | `PlayerThrower.SpawnProjectile` |
| 착탄은 화면마다 일어나지만, **효과는 대상의 결정권자 화면에서만 적용**한다 (플레이어 = 본인, 적 = 방장) | `ThrownProjectile.HasAuthority` |
| 플레이어가 맞으면 다른 화면은 피해를 **요청**만 하고, 본인 화면이 무적·피해 비율을 적용해 확정한 뒤 HP를 알린다 | `RequestDamage` → `SyncHp` |
| 포션 소모는 던진 사람 화면에서만 처리한다 | `PlayerAttackState` |

**보완할 점**
- **판정 권한을 반드시 넣는다.** 각자 궤적을 계산하면 4명 화면에서 착탄이 4번 일어난다. "그러면 피해가 4번 들어가지 않나?"가 가장 먼저 나올 질문이다. 답은 이미 구현돼 있다.
- **비교 수치를 넣는다.** 투사체를 위치 동기화 오브젝트로 만들면 팀 동기화 컴포넌트 기본값 기준으로 초당 10회 위치를 보낸다(`WorldTransformSync.m_sendRate`). 지금 방식은 던질 때 1회다. 생성·삭제 동기화도 필요 없다.
- **"위치가 다를 수 있음"을 정확히 쓴다.**

  | 구분 | 내용 |
  |---|---|
  | 같은 것 | 궤적 모양. 초기값과 물리 스텝(0.02초)이 같으므로 같은 포물선을 그린다 |
  | 다른 것 | **출발 시각**. 받는 쪽은 전송 지연만큼 늦게 출발한다 |
  | 실제로 문제가 되는 것 | **대상의 위치**. 적은 방장 화면이 기준이다. 던진 사람 화면에서는 맞았어도 방장 화면에서 적이 이미 움직였으면 피해가 들어가지 않는다 |

  즉 문제는 "포션 위치가 조금 다르다"가 아니라 **"내 화면에서 맞았는데 피해가 안 들어갈 수 있다"**이다. 이렇게 써야 지연 보상이 왜 필요한지 설명된다.
- **구 콜라이더가 여기서도 도움이 된다.** 랜덤 회전은 화면마다 다르지만 구는 회전해도 충돌 범위가 같다. 2-3의 결정이 멀티에서 궤적을 일치시키는 데도 쓰였다고 연결할 수 있다.
- **지연 보상은 "할 수 있다"가 아니라 계획으로 쓴다.**

  | 순서 | 내용 |
  |---|---|
  | 1. 측정 | PC 2대 또는 Photon 지연 시뮬레이션으로 지연 100ms / 200ms에서 착탄 시각 차이와 판정이 갈리는 빈도를 잰다 |
  | 2-a. 출발 시각 보정 | 발사 시각(서버 시간)을 함께 보내고, 받는 쪽이 지난 시간만큼 궤적을 앞당겨 시작한다. 궤적이 공식으로 계산되므로 비용이 작다. 건너뛴 구간에 벽이 있는지는 따로 검사해야 한다 |
  | 2-b. 던진 사람 기준 판정 | 던진 사람 화면에서 맞은 대상을 결정권자에게 요청으로 보낸다. 협동 게임에서는 조작한 사람의 화면과 결과가 맞는 편이 체감이 좋다 |

  측정 결과가 나오면 "지연 200ms에서 판정 불일치 N% → 보정 후 M%"처럼 수치로 쓸 수 있다. 이 항목이 **메인 소재**가 된다.

**다듬은 문장**
> 투사체를 네트워크 오브젝트로 만들지 않고, 던질 때 발사 위치·초기 속도·중력·포션 Id만 한 번 보내 각 클라이언트가 같은 궤적을 계산하게 했다. 착탄 효과는 대상의 결정권자(플레이어 본인, 적은 방장) 화면에서만 적용해 피해가 한 번만 들어간다.

## 3. "이후 구현 예정" 수정

**초안**: 각 포션마다의 효과 구현

**확인한 사실**: 효과를 조합하는 **구조는 이미 구현**돼 있다.

| 구성 | 내용 |
|---|---|
| `PotionEffect` (추상 클래스) | 효과 하나. 피해 / 회복 / 상태이상 3종이 있다 |
| `PotionData.effects` | 서로 다른 효과를 한 리스트에 저장한다 (`SerializeReference`) |
| `PotionTargetFlags` | 효과마다 적용 대상(아군 / 적 / 모두)을 정한다. "적에게 피해 + 아군에게 회복"을 한 포션에 넣을 수 있다 |
| `PotionDataEditor` | 인스펙터의 "효과 추가" 메뉴. 효과 클래스를 자동으로 찾아 보여 준다 |
| `PotionDatabase` | Id로 포션을 찾는다. 네트워크와 저장에는 Id만 쓴다 |

- 포션 23종 가운데 효과가 연결된 것은 **화염 물약 1종**이다 (적에게 화상 + 피해 5).
- 따라서 이렇게 고친다.

| 구분 | 내용 |
|---|---|
| 구현 완료로 옮길 것 | 코드 수정 없이 효과를 조합하는 포션 효과 구조 |
| 이후 구현 예정 | 나머지 포션의 효과 데이터 연결, 새 효과 종류(넉백·장판·저항 등 지금 3종으로 표현할 수 없는 것), 던지기 지연 보상(2-6), 필드 포션 줍기 동기화(2-2) |

### 코드 정리
포트폴리오에 적은 내용과 코드가 어긋나 보일 수 있는 부분이다.

| 항목 | 위치 | 이유 |
|---|---|---|
| 감지할 때마다 로그 출력 | `ItemPickupController.Scan`의 `Debug.Log` | 문자열을 만들므로 "할당 없는 감지"라는 설명과 맞지 않는다 |
| 상태이상 아이콘 미연결 | `StatusPanelPresenter.GetIcon` | HUD 영상에 아이콘이 비어 보인다 |
| 조준선이 적을 통과 | `Player.prefab`의 `obstacleLayers` | 2-3의 남은 차이 |
| 내용과 다른 주석 | `PotionSlotPresenter`, `StatusPanelPresenter`의 "(뼈대)" | 구현이 끝난 코드다 |
| 쓰지 않는 메서드 | `ThrowAimIndicator.GetImpactRadius` | 삭제 |
| 중복 코드 | `PlayerFSM.ConsumeAttack`의 `hasPotion` 재검사, `SaveData`의 슬롯 Id 반복문 | 바로 앞에서 같은 일을 이미 한다 |
| `public` 설정 필드 | `PlayerInputReader`, `ItemPickupController`, `ThrownProjectile` | 팀 컨벤션은 `[SerializeField] private`이다. 이름을 바꾸면 프리팹 연결이 끊기므로 `FormerlySerializedAs`를 붙인다 |
| null 확인 없음 | `PotionLoadout.Restore`의 `PotionDatabase.Instance` | DB 에셋이 없으면 불러오기와 동기화에서 오류가 난다 |
| 가이드 문서 | `PotionPrefabVariant.md` 4장 | BoxCollider 안내가 실제 프리팹(구 콜라이더)과 다르다 |
